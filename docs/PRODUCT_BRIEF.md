# 走马 · Zouma：产品与开发总纲

**行在途中，思入深处。**

英文副标题：**Conversation-Native Learning**。产品定位：**Conversation-Native Adaptive Learning System（对话原生自适应学习系统）**。本总纲描述产品目标与实施原则；当前已实现范围和验收状态以 [README](../README.md) 与 [VALIDATION](VALIDATION.md) 为准。品牌与兼容命名见 [BRAND](BRAND.md)。

## 1. 项目定位

走马是一个以对话为核心、以 AI 教学 Agent 为驱动、能够跨场景持续学习的开源自适应学习系统。

“走马”取行动之意，表达**人在行走，思想却能深入**的愿景。散步与通勤是最初的使用场景，长期方向是通过实时对话、主动思考、知识整合和持续反馈，探索不依赖固定书桌与屏幕的学习方式。

产品以类似自然实时对话的语音交互为重要入口，具备持久课程状态，并逐步建立教学决策能力。未来支持语音、文本、图表、数学推导与编程实践之间的连续切换。长期学习者记忆、知识追踪与自适应策略属于后续阶段；当前 v0.2 仍需完成真实模型与语音 P0 验收。

用户导入 Lecture、教材、PDF 或论文后，系统将其组织成适合口头讲授的课程。AI 持续讲解，用户能够随时打断、追问、质疑、用自己的语言解释概念，或展开自由讨论。讨论结束后，系统必须准确恢复原课程主线，并在下次使用时继续学习。

项目的核心价值包括：

- 让学习更容易开始。
- 让听讲与主动思考自然交替。
- 让讨论不会破坏课程连续性。
- 让学习记录逐步形成长期知识积累。
- 最终把概念理解连接到 Python、数学推导和实际练习。

项目的核心价值来自可持续的教学对话、可靠的课程连续性和逐步积累的学习证据。

## 2. 五个核心用户需求

### 2.1 降低学习启动成本

尽量减少准备设备、打开资料、选择内容和配置环境的负担。

目标体验是：完成首次设置与材料导入后，戴上耳机、点击继续即可开始学习。尤其关注注意力调节困难用户的操作负担，但不宣称医疗效果。

产品设计应减少不必要的菜单、选择和中断，默认提供清楚的下一步。

### 2.2 支持行走时的思考

将散步视为重要使用场景，支持概念理解、推理、知识迁移、联想和创造性讨论。

“部分用户在行走时更容易开放思考”属于需要验证的产品假设，不应预先当作对所有用户成立的事实。

不能让关键学习流程依赖持续看屏幕。图表、公式和代码需要提供适合口述的解释，并允许用户稍后回到视觉材料。

### 2.3 让不同场景中的学习形成连续积累

通过短知识单元、即时反馈和可靠续学，让学习在不同场景和会话之间保持连续。通勤是首批验证场景之一，课程连续性与深入理解是设计目标。

不以增加收听时长作为主要目标。更重要的是有效学习时间、理解程度、知识保留和持续使用的真实价值。

一次学习结束后，应清楚知道学到了哪里，以及下次从哪里继续。

### 2.4 支持费曼式主动学习

用户不仅提出问题，也可以用自己的语言解释概念、提出反例或展示推理过程。

AI 应帮助发现理解漏洞、区分表面复述与真正理解，并建立不同知识之间的联系。

长期方向是主动知识建构，而非持续的信息灌输。

### 2.5 成为实时私人导师与讨论伙伴

追求类似自然实时语音对话的体验：

- AI 能持续讲授。
- 用户可随时通过说话打断。
- 用户可以连续追问，不限于一问一答。
- AI 可以解释、引导，也可以平等讨论。
- 讨论结束后，准确回到原课程位置。
- 不依赖用户自己记住“刚才讲到哪里”。

## 3. 五个核心系统能力

### 3.1 Lecture-to-Interactive-Audio

将原始材料转换为结构化、适合口语讲授的课程，而非直接 TTS 朗读。

课程应尽量包含：

- 章节与知识单元。
- 学习目标和关键概念。
- 必要的先修知识。
- 适合口述的讲解、例子与过渡。
- 原文依据与来源定位。
- 适当的理解检查点。
- 可选的后续练习。

区分原文内容、教学改写和补充解释。不能编造来源；材料不足时应明确说明。

### 3.2 Stateful Conversation Orchestration

由应用管理课程主线、播放位置、讨论分支和恢复行为。

需要支持：

- 实时打断。
- 多轮自由讨论。
- 讨论后恢复课程节点。
- 暂停与重新进入。
- 页面刷新、断线及服务重启后的状态恢复。
- 防止旧语音、旧回答或旧保存请求覆盖新状态。

课程连续性不能只依赖模型的聊天上下文。

### 3.3 Pedagogical Agent

逐步建立教学决策能力，根据用户表现选择：

- 继续讲解。
- 换一种方式解释。
- 提问检查理解。
- 补充先修知识。
- 提供例子、反例或类比。
- 安排复习或实践。

Agent 的价值应体现为更好的教学决策与状态管理。不要为了架构形式引入大量相互对话的 Agent。

### 3.4 Knowledge Tracing & Adaptive Curriculum

追踪真正的学习证据，识别薄弱概念，逐步调整学习路径。

区分：

- 听过。
- 能够复述。
- 能够解释。
- 能够迁移。
- 能够独立解决问题。

播放完成不等于掌握。没有证据时，不显示虚构的掌握率。

### 3.5 Theory-to-Practice Loop

将音频中学习的概念连接到后续 Python、数学推导和实践练习。

长期形成：

概念学习 → 主动解释 → 实践 → 反馈 → 更新学习者状态 → 调整后续教学。

## 4. 不可偏离的产品与技术原则

- **Conversation-Native**：以对话组织学习；实时语音是重要入口，屏幕、文本与后续多模态实践承接同一学习主线。
- **Agent-Centric**：重点投入教学编排、学习状态和教学决策。
- **Model-Agnostic**：通过适配器接入 LLM、Realtime、STT、TTS，避免业务逻辑绑定单一供应商。
- **Open-Source First**：优先做可本地运行、可理解、可扩展的 GitHub 开源项目，再考虑商业化。
- **Evidence-Driven**：通过课程连续性、理解、知识保留、迁移和真实使用情况评价产品。
- **Low-Friction**：默认流程简单，减少学习前和学习中的操作负担。
- **Progressive Complexity**：先验证闭环，再增加复杂基础设施。

使用 API 是既定方向。当前不以训练或内置自有大模型作为开发前提。

## 6. 开发优先级

### P0：第一版必须实现的完整闭环

**Lecture 导入 → 课程结构化 → 实时语音讲授 → 随时语音打断 → 多轮自由讨论 → 准确恢复主线 → 保存进度。**

具体要求：

1. 至少支持一种可靠的材料导入方式，并保留来源定位。
2. 使用真实模型生成口语化、结构化课程。
3. 至少完成一个真实语音服务方案的端到端接入。
4. AI 讲授时，用户说话能够触发打断并停止当前输出。
5. 打断后可以连续讨论多个回合。
6. 用户表达继续学习后，系统能恢复原课程。
7. 课程、恢复位置和必要讨论记录能够持久保存。
8. 刷新、断线或重启后，能够从明确、可靠的位置继续。
9. 保留文字输入、文本讲稿和手动操作作为降级路径。
10. 完成首次配置后，日常续学尽量通过一个主要入口开始。

P0 可以采用明确的恢复粒度，例如课程节点、讲解单元或句子级。必须说明实际粒度，不能宣称未实现的毫秒级恢复。

### P1：第二阶段

- 跨会话学习者记忆。
- 主动口头提问与费曼式复述。
- 基础知识掌握度追踪。
- 课后知识总结。
- 基于已记录证据的简单复习建议。

这里的“跨会话学习者记忆”与 P0 的课程进度保存不同：P0 保存学到哪里，P1 逐步理解这个人掌握了什么、容易在哪里出错。

### P2：长期迭代

- 自适应课程规划。
- 动态教学策略。
- Python 与数学实践反馈闭环。
- 更多模型与语音供应商适配。
- 教学效果评估。
- 根据真实需求改进移动端、后台播放与锁屏体验。

模型可替换的接口设计属于 P0；完成大量供应商适配属于后续工作。

已有 Notebook 导出可以保留，但不能优先于实时语音与课程恢复。

## 7. 架构设计要求

在检查已有代码后，给出简洁、可实施的架构，并解释关键取舍。

建议保持以下模块边界，允许根据实际需要调整：

### 7.1 材料与课程层

负责材料解析、来源定位、课程结构化和课程版本。

课程内容应有稳定标识，避免改写课程后旧进度指向错误内容。

### 7.2 教学编排层

负责课程主线、当前教学活动、讨论分支与恢复策略。

至少明确区分：

- 讲授。
- 倾听与打断。
- 讨论。
- 恢复主线。
- 暂停。
- 完成。

讨论上下文与课程主线位置分别管理。即使讨论很长，也不能让课程位置漂移。

### 7.3 实时语音层

通过接口接入具体实现，可比较：

- 原生 Realtime 语音方案。
- 流式 STT + LLM + TTS 组合方案。

优先选择能够尽快验证自然交互、打断和恢复的方案。说明延迟、成本、可替换性和实现复杂度的取舍，不需要首版同时实现两套方案。

不要把供应商专有的会话对象直接当作应用的永久课程状态。

### 7.4 状态与事件层

持久保存：

- 课程与课程版本。
- 当前课程节点。
- 实际播放到的可靠检查点。
- 讨论开始时的恢复位置。
- 已完成问答与必要讨论摘要。
- 学习事件。
- 后续教学决策所需的证据。

不能把“已经向语音服务发送”当作“用户已经听到”。

需要处理取消、迟到响应、版本冲突、断线与恢复。防止旧请求把用户拉回旧位置。

### 7.5 学习者与教学策略层

先保留合理的数据接口，再逐步实现知识追踪与自适应。

课程内容、学习事件、掌握度推断和教学决策应保持可区分，便于解释与评估。

### 7.6 实践层

保留课程概念与练习之间的关联。

后续接入代码执行时，应使用隔离环境；当前服务端不得直接执行用户或模型生成的任意代码。

## 8. 推荐实施顺序

### 第一步：审查现状并校准范围

读取已有文档、代码与测试。

输出：

- 已实现。
- 部分实现。
- 尚未实现。
- 与本产品原则冲突之处。
- 达到 P0 的最短实现路径。

更新项目文档，明确当前原型与目标 MVP 的差距。

### 第二步：先打通实时语音技术闭环

使用短课程验证：

讲授 → 用户语音打断 → 连续讨论 → 用户要求继续 → 恢复原位置。

这一阶段优先解决实时交互和状态正确性，避免同时扩展大量材料格式或教学功能。

### 第三步：接入真实课程结构化

将已有材料导入接到真实模型生成流程。

检查口语表达、原文忠实度、概念覆盖、公式解释和来源定位。

### 第四步：完成可靠持久化与异常恢复

处理：

- 页面刷新。
- 网络断开。
- 语音服务中断。
- 模型超时。
- 用户切换课程。
- 多次快速打断。
- 旧回答迟到。
- 服务重启。

异常恢复后必须有明确状态，不能悄悄跳过未听内容。

### 第五步：优化低操作负担体验

围绕散步和通勤，检查：

- 是否容易开始。
- 是否必须频繁看屏幕。
- 是否能自然提出问题。
- 是否容易结束讨论并继续。
- 是否清楚保存到哪里。
- 是否能够快速开始下一次学习。

### 第六步：完成验收与开源交付

提供可运行项目、使用说明、配置示例、测试、架构说明、已知限制和下一阶段计划。

本地开发、整理和测试可以持续推进。创建远程仓库、发布、部署或产生外部费用时，按实际授权处理。

## 9. P0 验收标准

必须通过完整用户路径验证：

1. 用户导入一份短教材或 Lecture 文字稿。
2. 系统生成有原文依据、适合口述的结构化课程。
3. 用户开始听讲。
4. 用户在讲授中通过说话打断。
5. 当前语音停止，进入讨论。
6. 用户连续追问，并提出课程外但相关的讨论。
7. 用户要求继续课程。
8. 系统回到原主线的正确位置，必要时提供简短衔接。
9. 没有跳过未听内容，也没有重复大段已听内容。
10. 关闭再打开后，课程与可靠检查点仍在。
11. 网络或模型失败时，不丢失已保存进度。
12. 不支持语音或语音失败时，有可理解的降级方式。

同时记录：

- 从用户打断到 AI 停止输出的延迟。
- 从用户说完到回答开始的延迟。
- 恢复位置的正确性。
- 意外跳课、重复或状态丢失次数。
- 完成一次有效学习所需的操作负担。

延迟目标应结合所选技术和实测结果制定，不得用未经测量的数字宣称达标。

## 10. 后续教学效果评估

逐步使用以下指标：

- 概念解释准确性。
- 费曼式复述中的理解漏洞。
- 延迟复测中的知识保留。
- 新情境下的知识迁移。
- 练习独立完成情况。
- 用户是否愿意在真实通勤或散步场景持续使用。
- 课程连续性与主观操作负担。

收听时长、播放完成率和聊天次数只作为辅助信号。

## 最重要的判断标准

让学习更容易开始，让思考能够自然发生，让每一次对话都成为长期知识积累的一部分。

任何功能或架构调整，都应说明它如何改善学习启动、主动思考、课程连续性或长期学习效果。
